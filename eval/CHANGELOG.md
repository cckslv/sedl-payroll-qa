# 评测集变更记录

> 为什么要有这个文件：评测集本身也是代码，改了就改变了分数的含义。
> 没有变更记录，跨版本比较准确率就没有意义。

## 2026-11-02 · 首版建立

- 建立 20 题评测集（`questions.jsonl`），按类型分：单值 3、聚合 3、排序 4、过滤 3、考勤 2、多表 2、参数 2、边界 1
- 评测口径：执行准确率（跑 gold SQL 与模型 SQL，结果集规范化后比较），**不比 SQL 文本**

### 首轮跑分：严格 85.0%（17/20）

暴露了三处问题，逐条处理：

| 题 | 问题 | 处理 |
|:--|:--|:--|
| q14 | **gold 写错**：问句是「3月份**每个人**应出勤多少小时」，gold 却写成 `SELECT DISTINCT schedule_hours`，只返回 1 行 176。问的是"每个人"，答案就该是 8 行 | 改为 `SELECT e.name, a.schedule_hours ... JOIN employee` 按人返回。⚠️ **此修改发生在首次 git 提交之前，历史里没有原始错误版本**，只能在此记录 |
| q17 | 模型返回了 `name, value, unit, note` 四列，gold 是两列。内容正确，只是多给信息 | 引入**宽松口径**：行数一致时，允许 gold 的每行按前缀匹配到模型结果的某一行 |
| q13 | 问「1月份应出勤小时数是多少」，8 个人值都是 168，gold 靠 `DISTINCT` 才唯一；模型返回 8 行重复值 | **保留为 FAIL，不修改 gold**。这是"题目本身有歧义"的样本，留着提醒自己 |

### 第二轮：收紧澄清提示词后重跑

原提示词让模型"没说清楚就反问"，导致 q13 被反问（"请问要查询哪位员工？"）。
改为：只有缺少关键信息、无法确定查询范围时才澄清；全局问题不要反问是哪个人。

**结果：严格 90.0%（18/20）/ 宽松 95.0%（19/20），20 题共 25 秒。**
